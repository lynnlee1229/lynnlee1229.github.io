Read, predict, execute, explain

Two university courses supply complementary foundations: Berkeley CS267 for parallel machines, communication and load balance; MIT 6.5840 for distributed-system failure and MapReduce. Neither substitutes for the pinned Spark 3.5.8 implementation guides. Choose these relevant units instead of treating an entire graduate course as a prerequisite for this introductory Lab.

The reviewed catalogue below is searchable in both languages and downloadable as structured JSON. Each learning unit names a particular lecture, paper section or assignment specification and a separate original runnable exercise. Predict the result before running, verify the stated invariant, then explain the observed plan and counters. The mapping does not grant credit or reproduce a university assignment solution.

Verification date: 14 November 2026, Asia/Shanghai. Published material is distinguished from tentative schedules. The CS267 2016 archive is deliberately historical; its hardware figures are not 2026 capacity advice. The 2025 official page says its videos require a Berkeley login. MIT's selected Spring 2026 Lecture 1 notes and Lab 1 specification are already published, while its schedule retains a tentative label. Public reading access is separate from enrollment, grading and tuition. No private course account or paid material is used.

01-parallel · Work, slots and granularity

  • CS267 Lecture 1: Introduction — Lecture 1 (19 Jan 2016): motivation and parallel performance
  • CS267 Lecture 3: Parallel Machines and Programming Models — Lecture 3 (26 Jan 2016): machine and programming models
python scripts/run_all.py --only parallel

Predict first: With two slots, predict whether 64 tiny tasks beat eight. Explain why task count does not mean 64 cores.

Evidence to defend: Every result equals independent sum 119516556; inspect 1/8/64 TaskEnd attempts and all timings.

Limits: local[2,2], one JVM; neither the cost widget nor the run proves machine scaling.

Original Lab exercise; upstream assignment solutions are not included.

02-model · MapReduce to DAG and stages

  • 6.5840 2026 Lecture 1: Introduction — CASE STUDY: MapReduce; The shuffle; Coordinator
  • MapReduce: Simplified Data Processing on Large Clusters — Sections 2 and 3: model and implementation
  • CS267 Lecture 9: Cloud Computing and Big Data Processing — PDF pages 30–47: MapReduce, recovery and Spark concepts
python scripts/run_all.py --smoke --only aggregation

Predict first: Draw map-side work, exchange and reduce-side work before running. Which dependency causes a stage boundary?

Evidence to defend: Find ShuffledRDD in both saved lineages and two task stages in each measured group; output still matches all key totals.

Limits: This RDD trace illustrates the model; it does not implement MIT Lab 1 or its RPC coordinator.

Original Lab exercise; upstream assignment solutions are not included.

03-aggregation · Mergeable summaries before movement

  • MapReduce: Simplified Data Processing on Large Clusters — Section 4.3: Combiner Function
  • Apache Spark 3.5.8 RDD Programming Guide — Working with Key-Value Pairs; reduceByKey versus groupByKey
python scripts/run_all.py --only aggregation

Predict first: Explain why summing locally preserves a monoid; why averaging local means without counts fails.

Evidence to defend: Compare the full 1,000-key oracle and Shuffle bytes; distinguish serialized batches from source records.

Limits: Local Shuffle bytes measure engine serialization, not cross-host network traffic.

Original Lab exercise; upstream assignment solutions are not included.

04-join · Skew, replication and the long tail

  • CS267 Lecture 23: Dynamic Load Balancing — Lecture 23 (12 Apr 2016): task granularity and dynamic load balancing
  • Apache Spark 3.5.8 SQL Performance Tuning — Join Strategy Hints; broadcast and merge hints
python scripts/run_all.py --only join

Predict first: Predict the hottest output partition under 80% hot-key skew; what extra work does salting add?

Evidence to defend: All variants: 240000 rows, weighted sum 384001; compare partition histograms and SortMergeJoin/BroadcastHashJoin plans. Keep the slower salted observation.

Limits: Unique dimension keys. The old join plans are pre-action strategy evidence, not final AQE plans; AQE skew join remains untested.

Original Lab exercise; upstream assignment solutions are not included.

05-recovery · Determinism, retry and lineage

  • 6.5840 Lab 1: MapReduce — Introduction; Your Job; worker timeout and crash tests (study only)
  • MapReduce: Simplified Data Processing on Large Clusters — Section 3.3: Fault Tolerance
  • Resilient Distributed Datasets: A Fault-Tolerant Abstraction for In-Memory Cluster Computing — Sections 2.1 and 5: abstraction and implementation, recovery/checkpointing
python scripts/run_all.py --only recovery

Predict first: Which result survives one task exception? What changes when a cache block is removed?

Evidence to defend: One failed then successful partition-0 attempt; evaluations 8/0/8; ReliableCheckpointRDD truncates lineage.

Limits: No killed executor or host. Local checkpoint cannot survive host loss; this is weaker than MIT worker-crash testing.

Original Lab exercise; upstream assignment solutions are not included.

06-resources · Memory hierarchy and diagnosis

  • CS267 Lecture 2: Single Processor Machines: Memory Hierarchies and Processor Features — Lecture 2 (21 Jan 2016): locality and memory hierarchy
  • Apache Spark 3.5.8 Tuning Guide — Memory Management Overview; Memory Tuning
python scripts/run_all.py --only resources

Predict first: Will more partitions change the working set even with unchanged slots? Distinguish CPU caches from persisted RDD storage.

Evidence to defend: Validate sorted payloads, row count and ID sum; inspect nonzero real Spill and per-task memory counters.

Limits: Spill is forced by 8192 elements, not natural OOM; task peak execution memory is not process RSS.

Original Lab exercise; upstream assignment solutions are not included.

07-aqe · Observe a final adaptive plan

  • Apache Spark 3.5.8 SQL Performance Tuning — Adaptive Query Execution → Coalescing Post Shuffle Partitions
  • CS267 Lecture 23: Dynamic Load Balancing — Dynamic scheduling and task-size overhead as conceptual background
python scripts/run_aqe.py

Predict first: Predict why merely enabling AQE may leave 32 reducers, and whether 1-byte versus 1-MiB targets produce the same final plan.

Evidence to defend: Full per-key count/sum oracle; compare pre/final plans, AQEShuffleRead SQL metrics and actual TaskEnd stages. Run the 1-byte counterexample in the walkthrough.

Limits: Only post-shuffle coalescing is implemented. Join adaptation, distributed training and inference remain reading extensions.

Original Lab exercise; upstream assignment solutions are not included.

AI reading bridge · not implemented

Training: read ZeRO (2019 preprint, selected 2020 v3). Relate state sharding to per-worker memory and collective communication; data shards and optimizer-state shards are different. Write which values each rank owns, and when they must move. Spark aggregation is a prerequisite reasoning exercise, not a ZeRO implementation or GPU benchmark.

Inference: read Orca (OSDI 2022), especially iteration-level scheduling. Relate variable request lengths to the long-tail and task-granularity questions from Join skew and AQE. Explain why a request can finish while its batch peers continue. Tail latency, token throughput, GPU collectives and serving correctness were not measured; this Lab runs no model and makes no LLM evaluation claim.

These are already published primary papers, not a forecast or a claim to cover the latest 2026 systems. No paid calls or credentials are needed.
