Relational and nonrelational databases

A relational database organizes data into relations, with keys and constraints describing valid rows and relationships. SQL supports filtering, joins, aggregation, and other operations over those relations. This is useful when a system needs explicit consistency rules and queries that combine several entities.

NoSQL is a family of approaches rather than a single storage model. Redis is commonly used as a key-value/data-structure store, MongoDB as a document database, and HBase as a wide-column store. These systems should not all be described as in-memory key-value databases.

Logs, geospatial information, large datasets, and highly available services can motivate a nonrelational design, but none of those requirements selects a database automatically. Compare query patterns, consistency requirements, partitioning, operational complexity, and recovery behavior. “No SQL parser” does not by itself establish higher performance, nor does a relational model prevent horizontal scaling.

Storage engines: InnoDB and MyISAM

MySQL supports engines including InnoDB, MyISAM, MEMORY, and ARCHIVE. InnoDB is the default and the usual starting point for transactional applications.

The older claim that InnoDB lacks full-text indexes is incorrect for MySQL 8.0. See InnoDB full-text indexes . Neither engine is universally faster; workload and required guarantees determine the comparison.

Normalization, keys, and constraints

The first three normal forms are useful tools for reducing avoidable redundancy:

  1. First normal form: represent attributes as single values within the chosen domain, rather than repeating groups inside a row.
  2. Second normal form: non-key attributes depend on the whole candidate key, not only part of a composite key.
  3. Third normal form: avoid transitive dependencies of non-key attributes on a key through other non-key attributes.

For example, an order-line table keyed by (order_id, product_id) should not repeat an order’s customer address on every line merely because the application can do so. Separate entities according to their dependencies, then introduce denormalization only for a justified access pattern and an explicit update strategy.

A superkey is any attribute set that uniquely identifies a row. A candidate key is a minimal superkey: removing an attribute would lose uniqueness. The primary key is the candidate key selected as the table’s main identifier. A foreign key expresses a reference to a key in another table, or sometimes the same table.

Common SQL constraints are NOT NULL, UNIQUE, PRIMARY KEY, FOREIGN KEY, and CHECK. A table has one primary-key definition, which can contain multiple columns. It can have several unique constraints. Nullable unique columns require care because their treatment of NULL differs from ordinary equal values. MySQL began enforcing CHECK constraints in 8.0.16; older-version assumptions must not be carried forward without verification. See CHECK constraints .

CHAR and VARCHAR

CHAR(n) describes a fixed-length character value with padding semantics. VARCHAR(n) stores a variable-length value with length information. The declaration is in characters, while storage depends on the character set and the encoded byte length. VARCHAR length overhead is not always one byte.

Use the domain to guide the choice: a fixed-format country code differs from a free-form display name. There is no general rule that CHAR queries are faster than VARCHAR queries. Padding, collation, index width, and the actual workload matter. Details are in the CHAR and VARCHAR documentation .

IN and EXISTS

IN asks whether a value belongs to a result set. EXISTS asks whether a subquery returns at least one row. An optimizer can transform either form, so neither keyword specifies a mandatory hash join or nested loop.

SELECT p.id
FROM product AS p
WHERE EXISTS (
  SELECT 1
  FROM order_item AS oi
  WHERE oi.product_id = p.id
);

Choose a form that expresses the intended semantics, then inspect the plan. Table size alone does not prove that one form is always faster. MySQL’s semijoin transformations explain why apparently different subqueries can share execution strategies.

NOT IN also requires attention to NULL: a null in the subquery result can make comparisons unknown. A correlated NOT EXISTS expresses absence differently. Establish semantic equivalence before comparing performance; “NOT EXISTS always uses indexes and is always faster” is not a sound rule.

DELETE, TRUNCATE, and DROP

StatementMain effectImportant behavior in MySQL
DELETERemoves matching rowsSupports WHERE; InnoDB changes can be rolled back before commit; DELETE triggers run
TRUNCATE TABLERemoves all rows while retaining the table definitionDDL with an implicit commit; resets the auto-increment counter; does not invoke DELETE triggers
DROP TABLERemoves the table definition and its dataDDL; ordinary transaction rollback is not an undo mechanism

With autocommit enabled, an individual DELETE normally commits automatically; it does not always wait for a separate application COMMIT. Space reclamation depends on the engine and tablespace arrangement. TRUNCATE is not simply an unlogged sequence of row deletes, and foreign-key relationships restrict where it can be used. See TRUNCATE TABLE .

Choose DELETE for a selective or transactional removal, TRUNCATE for an intentional whole-table reset, and DROP when the table itself is no longer required. Check the target and recovery plan before destructive operations.

Stored procedures

A stored procedure packages SQL and procedural logic inside the database under a callable name. It can reduce network round trips and centralize operations or permissions. MySQL stored-program syntax should not be confused with SQL Server’s T-SQL.

The tradeoffs include deployment and versioning, observability, testing, portability, and ownership of business logic. Rapidly evolving services may prefer application code for these reasons. The decision should follow the team’s maintenance model; a procedure is not automatically faster merely because it is stored in the database.

How a SELECT reaches the storage engine

MySQL separates server responsibilities from storage-engine responsibilities. A useful conceptual sequence is:

Connection and authentication
    -> parsing and name resolution
    -> optimization
    -> execution
    -> storage-engine access
    -> result delivery

The connection layer establishes a session and authenticates it. Parsing identifies tokens and checks SQL grammar. Preparation resolves tables and columns and expands constructs such as SELECT *. The optimizer chooses an execution plan, considering available paths and estimated costs. The executor invokes engine operations to obtain and process records.

The old server query cache was removed in MySQL 8.0. It should not appear as an active stage in an 8.0 execution diagram. Nor should a conceptual diagram be read as a promise about internal function names, which change across implementations and releases.

For a primary-key equality lookup:

SELECT * FROM product WHERE id = 1;

The engine can locate the matching clustered-index record, return it if visible, and finish without scanning the entire table. If no usable index supports the following predicate, the executor may instead scan records and filter them:

SELECT * FROM product WHERE name = 'iphone';

EXPLAIN makes the chosen access path inspectable. The existence of an index is not enough; inspect the actual plan and workload.

Index condition pushdown

Consider an index on (age, reward) and this query:

SELECT * FROM t_user
WHERE age > 20 AND reward = 100000;

The age condition can define the main scan range. Although reward may not narrow that range, the engine can test it from the secondary-index entry before fetching the full row. This is index condition pushdown, indicated by Using index condition in applicable plans. It reduces unnecessary clustered-index lookups; it does not mean every predicate becomes a search-range boundary. See index condition pushdown .

Where InnoDB stores rows

The configured data directory can be inspected with:

SHOW VARIABLES LIKE 'datadir';

With file-per-table tablespaces, a table commonly has an .ibd file containing its data and indexes. Shared and general tablespaces also exist, so “every table always has a separate .ibd file” is too broad. MySQL 8.0 uses a transactional data dictionary rather than the old .frm metadata-file model; this is more than simply moving the contents of .frm into another filename. See the MySQL data dictionary .

The conceptual hierarchy is tablespace, segment, extent, page, and record. InnoDB normally uses 16 KiB pages, although page size is configurable. At that page size, an extent contains 64 pages, totaling 1 MiB. Extent allocation helps manage larger contiguous areas, but logical neighbors are not guaranteed to remain physically adjacent forever.

An index uses segments for leaf and nonleaf pages. Other page types serve purposes such as undo and overflow storage. Page organization is fundamental to the storage engine, but should not be interpreted as a claim that every operating-system I/O request has exactly the configured page size.

Reading the COMPACT record layout

InnoDB supports REDUNDANT, COMPACT, DYNAMIC, and COMPRESSED row formats. DYNAMIC is the normal modern default; COMPACT is useful for studying the layout because its record metadata is easy to reason about.

Variable-length field lengths | NULL bitmap | Record header | Field data

Use this small schema to reason about variable fields:

CREATE TABLE t_user (
  id INT NOT NULL,
  name VARCHAR(20) DEFAULT NULL,
  phone VARCHAR(20) DEFAULT NULL,
  age INT DEFAULT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARACTER SET=ascii ROW_FORMAT=COMPACT;

For illustrative values name='a' and phone='123', the encoded lengths are one and three bytes. The length entries are organized in reverse field order. A null variable-length field does not contribute its usual data bytes and length entry.

The NULL bitmap has one bit per nullable field, not one bit per field that happens to be null in the current row. With nullable name, phone, and age, a row where all three are present has a zero bitmap; a row where phone and age are null has the corresponding two bits set. Nine nullable fields require two bytes. A table with no nullable fields does not need this bitmap.

The record header includes a deletion mark, a link to the next record, and the record type. A deletion mark does not mean the bytes remain forever: purge can later reclaim obsolete records when transaction visibility permits it. Record types distinguish ordinary records, internal-node records, and boundary records.

Clustered records also carry transaction metadata: a six-byte transaction ID and a seven-byte rollback pointer. If no primary key or suitable unique non-null key exists, InnoDB uses a hidden six-byte row ID for the clustered index. The rollback pointer connects to undo information rather than directly to a complete previous row. See InnoDB multi-versioning .

VARCHAR limits and overflow pages

VARCHAR(n) declares a maximum character count. MySQL’s logical row-size limit is 65,535 bytes, including relevant overhead, with special accounting for TEXT and BLOB. That limit is separate from InnoDB’s local on-page record limit. Character encoding and the other columns therefore matter.

The original exercise compared a nullable ASCII VARCHAR(65535) with VARCHAR(65532). The first exceeds the logical limit after overhead; reducing the declared size can satisfy that particular logical calculation. It is not a universal recommended column size or a guarantee for every engine configuration. In utf8mb4, a character can require four bytes, not three. See row-size limits .

When a long value is moved off-page, COMPACT retains an inline prefix and an overflow pointer. DYNAMIC and COMPRESSED can store the long value entirely off-page with a pointer in the record. The selection depends on value and row size; these formats do not put every variable-length value off-page. The exact behavior is documented in InnoDB row formats .

The practical connection is that schema choices affect record size, rows per page, buffer-pool use, and index width. Understanding the layout helps explain costs; measurements still determine whether a schema change is worthwhile.
