MySQL Study Notes: Transactions, Logging, and MVCC

An English reading edition of the 2023 notes, covering isolation, undo and redo, binary logs, commit coordination, replication, and buffer-pool behavior.

Historical notes, originally dated May 2023. This English reading edition consolidates repeated explanations and clarifies version-sensitive claims. It discusses MySQL 8.0 with InnoDB; older redo-file layouts are identified explicitly. The original date describes the Chinese note, not the date of this English adaptation. Examples are for an isolated test database.

Transactions and the ACID properties

A transaction groups related database operations into one unit of work. A transfer, for example, should not debit one account without also crediting the other. ACID describes four different responsibilities:

PropertyMeaningRelevant InnoDB mechanisms
AtomicityCommit the unit or undo its transactional changesUndo records and rollback
ConsistencyPreserve declared integrity rules and business invariantsConstraints plus correctly designed transactions
IsolationControl what concurrent transactions can observe and changeIsolation levels, MVCC, and locks
DurabilityRetain acknowledged commits under the configured failure modelRedo logging, flush policy, and reliable storage

Consistency does not follow from the other three properties without correct business logic. A perfectly atomic transaction can still transfer the wrong amount. Durability also depends on configuration and the storage stack; it is not an unconditional promise against every kind of failure.

What can concurrent transactions observe?

A dirty read observes another transaction’s uncommitted data. A nonrepeatable read observes a changed value when reading a row again. A phantom changes the set of rows matching a predicate, often through an insertion or deletion. These are different phenomena, not a universal ranking of business severity.

MySQL exposes four isolation levels:

LevelUseful mental model
READ UNCOMMITTEDA read can observe uncommitted changes
READ COMMITTEDEach consistent read gets a fresh committed-data snapshot
REPEATABLE READConsistent reads reuse the transaction’s established snapshot
SERIALIZABLEStronger serialization constraints introduce additional locking and waiting

InnoDB defaults to REPEATABLE READ. Higher isolation can reduce concurrency, but its performance effect depends on the workload; it is not a fixed ordering for every application.

START TRANSACTION starts an explicit transaction. Under REPEATABLE READ, its first consistent read normally establishes the snapshot; the BEGIN statement itself does not imply that the read view has already been created. START TRANSACTION WITH CONSISTENT SNAPSHOT requests a snapshot at transaction start under a supporting isolation level. See consistent nonlocking reads .

Snapshot reads and locking reads are different

An ordinary InnoDB SELECT usually performs a consistent nonlocking read under READ COMMITTED or REPEATABLE READ. It reconstructs a visible row version rather than locking every matching row. SELECT ... FOR UPDATE, SELECT ... FOR SHARE, and modifying statements use different locking and visibility rules.

Consider this sequence:

-- Session A, using REPEATABLE READ
START TRANSACTION;
SELECT * FROM student_demo WHERE id = 5;  -- No row exists

-- Session B
START TRANSACTION;
INSERT INTO student_demo (id, name, age) VALUES (5, 'Alex', 18);
COMMIT;

-- Session A
SELECT * FROM student_demo WHERE id = 5;  -- Snapshot still excludes B's row
UPDATE student_demo SET name = 'Sam' WHERE id = 5;
SELECT * FROM student_demo WHERE id = 5;  -- A can see its own modification
ROLLBACK;

The surprising result comes from combining a snapshot with a current modification and the rule that a transaction sees its own changes. Similarly, an ordinary SELECT and a later SELECT ... FOR UPDATE need not return the same set after another transaction commits. This is not evidence that two ordinary consistent reads arbitrarily abandon their established snapshot.

If correctness requires reserving a range against concurrent insertions, use the appropriate locking operation inside the transaction, with an index and isolation level that provide the required range protection. Do not mechanically add FOR UPDATE to every query: it changes contention and deadlock behavior.

Undo, redo, and the binary log

The three logs serve different purposes:

LogLayerMain role
UndoInnoDBRoll back changes and reconstruct older row versions
RedoInnoDBRecover page changes after a crash
Binary logMySQL serverRecord changes for replication and point-in-time recovery

Undo is not a complete backup of the database before each transaction, and redo is not a full copy of the database afterward. They record the information their respective mechanisms need. Undo pages themselves need recovery protection, so changes to those pages also generate redo.

Old undo versions cannot be purged while a transaction may still need them. Long-running snapshots can therefore increase retained history even when they perform no writes. See InnoDB multi-versioning .

Why the buffer pool needs write-ahead logging

InnoDB reads and caches pages in its buffer pool. The default page size is 16 KiB, though it is configurable when initializing an instance. Reading one row generally brings in its page, not a separate one-row cache entry.

An update changes a cached page and makes it dirty. Writing every dirty page immediately would make small random writes expensive. Write-ahead logging allows dirty pages to be flushed later, provided the necessary redo becomes durable before the corresponding page is written. A commit can complete without forcing all of its changed data pages to disk.

After a crash, recovery applies redo as needed and resolves incomplete transactions. It does not blindly preserve every update present in redo: uncommitted work must still be undone. Redo reduces the need to synchronously write scattered data pages for each commit; it does not eliminate those page writes altogether.

Redo starts in a log buffer and is written and flushed according to several triggers. A log write to the operating system is different from a flush that requests durable storage. The commit policy is controlled by innodb_flush_log_at_trx_commit:

ValueCommit-time behaviorMain exposure
1Write and flush redo at commitDepends on storage honoring durability requests
2Write redo at commit; flush periodicallyOS or power failure can lose recent commits
0Write and flush periodicallyA server-process failure can also lose recent commits

Periodic work is not an exact one-second loss bound: scheduling and configured flush intervals matter. Increasing innodb_log_buffer_size can reduce buffer-pressure writes for large transactions, but it does not replace commit durability. Check the InnoDB parameter definitions before changing these settings.

Redo capacity and checkpoints

Redo space is reused once recovery no longer needs the older records. A checkpoint advances the recoverable boundary as dirty pages are flushed. If redo generation outpaces flushing and reusable capacity runs low, foreground work can be throttled or stalled.

The original notes describe the older ib_logfile0 / ib_logfile1 arrangement. MySQL 8.0.30 changed redo-capacity management, introducing innodb_redo_log_capacity and a different file layout. Do not apply the old file-count diagram to all MySQL 8.0 releases. See redo log configuration .

Larger redo capacity may absorb bursts, but it is not a substitute for adequate sustained storage throughput. Measure redo generation, checkpoint age, dirty-page flushing, and recovery objectives together.

Binary-log formats and recovery

The binary log records data-changing events and relevant schema operations; ordinary reads are not its purpose. The three traditional formats are:

  • STATEMENT: records statements. Some statements are unsafe or nondeterministic for statement-based replication.
  • ROW: records row changes, avoiding many statement-replay ambiguities at the cost of potentially larger logs for large updates.
  • MIXED: switches between statement and row logging according to the statement’s characteristics.

MySQL 8.0 defaults to ROW, correcting the historical note’s blanket statement that STATEMENT is the default. Format behavior and options are documented under binary logging options .

Binary logs are appended and rotated, but retention can remove older files. They are not automatically an eternal, complete history. Recovering from an accidental deletion generally requires a suitable backup plus all required binary logs, replayed to the intended recovery point. Redo alone is not an undo button for an already committed deletion.

sync_binlog controls binary-log synchronization. A value of 1 synchronizes each commit group; larger values defer synchronization across groups, and 0 relies on the operating system. Group commit means a group may contain several transactions, so “lose exactly N transactions” is not an accurate general description of a value of N.

Why commit coordination is necessary

When binary logging is enabled, the server must coordinate its transaction record with the storage engine. Otherwise, recovery could retain an engine change absent from the binary log, or replication could replay a change that the source rolled back.

The conceptual sequence for transactional changes is:

Prepare the InnoDB transaction
    -> write the transaction's binary-log record
    -> make the required logs durable
    -> commit the storage-engine transaction

For a prepared transaction encountered during recovery, the durable commit decision determines whether to complete it or roll it back. This is internal transaction coordination, distinct from an application orchestrating distributed XA transactions across several database servers. See replication and transactions .

Multiple transactions can share log synchronization through group commit. A useful conceptual breakdown is flush, sync, and engine commit, with pipeline stages allowing concurrent progress. Exact internals vary by release. Do not estimate one physical fsync per transaction independently of batching.

binlog_group_commit_sync_delay and binlog_group_commit_sync_no_delay_count can trade a deliberate wait for larger groups. Their effect must be measured against transaction latency. They do not justify claiming that an unflushed operating-system page cache survives power failure.

Replication and acknowledgement boundaries

In conventional replication, the source exposes binary-log events, the replica receives them into relay logs, and its applier executes them. A received event and an applied event are different milestones. Replicas may use parallel appliers rather than one universal replay thread.

Asynchronous replication does not wait for a replica acknowledgement before returning a successful source commit. A failover can therefore lose transactions that were acknowledged by the old source but never reached the chosen replica. Reads routed to replicas can also be stale.

Semisynchronous replication waits for the configured acknowledgement condition. A replica acknowledgement means that the events have reached the required relay-log stage; it does not mean every replica has applied them. Timeouts may cause fallback to asynchronous operation, so semisynchronous replication is not an unconditional no-data-loss guarantee. See semisynchronous replication .

Adding replicas consumes source network and replication resources. Choose replica count from read demand, availability objectives, and failure-domain design rather than a universal “two or three replicas” rule.

Buffer-pool management and scan resistance

Three lists provide a useful learning model: the free list tracks available pages, the LRU structure manages replacement, and the flush list tracks dirty pages. A dirty page can belong to both the replacement structure and the flush list. Page metadata also consumes memory, so usable cached data is not equal to the configured byte count.

InnoDB uses a modified LRU policy with young and old regions. Newly read pages enter the old region; delayed promotion helps prevent read-ahead and large scans from evicting frequently used pages. innodb_old_blocks_pct and innodb_old_blocks_time control related behavior. See the buffer pool .

For example, a query returning only a few rows can still scan many pages:

SELECT * FROM user_demo WHERE name LIKE '%alex%';

The leading wildcard usually prevents a normal B-tree range lookup on name; inspect the actual plan. Result-set size alone says little about cache disruption.

Dirty pages are flushed in the background and under checkpoint or free-page pressure. Shutdown behavior also depends on shutdown settings, so avoid the absolute claim that every shutdown always writes every dirty page. Occasional latency spikes can coincide with flushing, but increasing the buffer pool or redo capacity is a hypothesis to test, not an automatic remedy.

When investigating I/O pressure, first separate data reads, data-page writes, redo synchronization, binary-log synchronization, and temporary-file activity. Inspect query plans, working-set size, memory headroom, and storage latency before weakening durability. A blanket percentage-of-RAM rule ignores connection memory, other processes, and container limits.

How a read view selects a row version

A conceptual read view captures the creating transaction, the set of active read-write transaction IDs, and lower and upper visibility boundaries. InnoDB row metadata includes a modifying transaction ID and a rollback pointer used to reconstruct older versions.

The visibility logic can be summarized as:

If the version belongs to this transaction: visible
If its transaction ID is older than the lower boundary: visible
If it is at or beyond the upper boundary: not visible
Otherwise: visible only if it was not active in this read view
If not visible: follow undo information to an older version

The active set belongs to the captured view. A transaction that was active when that view was created does not become visible within that same view merely because it commits later. READ COMMITTED sees its commit through a newer view on a later consistent read; REPEATABLE READ continues using the established view. Deletes, inserts, and the transaction’s own changes still need the engine’s full visibility rules.

This distinction explains a common experiment: transaction B reads a balance, transaction A updates but has not committed, and B still sees the old value. After A commits, B sees the new balance on its next ordinary read under READ COMMITTED, but normally retains the earlier snapshot under REPEATABLE READ.
