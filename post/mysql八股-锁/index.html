MySQL Study Notes: Locks, Lock Ranges, and Deadlocks

An English reading edition of the 2023 notes on global, table, metadata, intention, auto-increment, and row locks, with practical inspection and recovery guidance.

Lynn LeePublished 2023-05-178 min read
Read in Chinese →

An archived study note, kept with its original date. This English reading edition clarifies version-sensitive statements; the original Chinese is available via the language switch.

Historical notes, originally dated May 2023. The lock-range examples in the original used MySQL 8.0.26, InnoDB, and REPEATABLE READ. This English reading edition combines repeated examples and clarifies misleading generalizations. The historical date belongs to the Chinese note; this adaptation does not imply an English publication in 2023. Verify actual lock ranges on your exact release and execution plan.

Global read locks and logical backups

The traditional global read-lock command is:

FLUSH TABLES WITH READ LOCK;
-- Perform the operation that requires this lock.
UNLOCK TABLES;

It prevents relevant writes and schema changes while held. The owning session releases it with UNLOCK TABLES; disconnecting the session also releases its lock. Acquiring and holding it can disrupt production writes, especially during a long backup.

For transactional InnoDB tables, mysqldump --single-transaction can take a consistent snapshot while ordinary data changes continue. This does not make nontransactional tables consistent, and concurrent DDL requires care. MyISAM does not provide InnoDB’s transactional snapshot behavior. Select a backup method according to the engines, schema-change activity, and recovery requirements, then test restoration rather than only checking whether a dump file exists.

Explicit table locks

Table locks constrain both other sessions and the session that acquired them:

LOCK TABLES student_demo READ;
-- Read access is allowed under the lock; writing is not permitted.
UNLOCK TABLES;

LOCK TABLES student_demo WRITE;
-- Exclusive table access by this session.
UNLOCK TABLES;

The owning session cannot simply upgrade a READ lock by issuing a write; an attempted write can fail with an error. Other sessions’ conflicting operations wait. Explicit table locking has transaction and implicit-commit implications, so it should not be casually mixed into an InnoDB transaction that relies on row locking.

Metadata locks protect the table definition

Metadata locks, or MDL, are acquired automatically when statements use database objects. They keep a table definition stable while a transaction uses it. DDL needs a compatible metadata-lock state before it can proceed.

A typical blocking chain is:

  1. Session A starts a transaction, reads a table, and stays open.
  2. Session B requests a schema change and waits for conflicting MDL.
  3. Later requests can queue behind the pending DDL, causing a growing backlog.

The simplified “MDL read versus write” model is useful, but the implementation has multiple lock types and scheduling rules. Inspect performance_schema.metadata_locks and transaction age before a schema change. Resolve a long transaction deliberately; killing it can trigger a lengthy rollback and is not a cost-free fix. See metadata locking .

Intention locks coordinate row and table locking

Before acquiring shared row locks, InnoDB acquires an intention shared lock, IS, on the table. Exclusive row locking uses an intention exclusive lock, IX. These tell a conflicting whole-table lock request that finer-grained locks may exist, without requiring a scan of every row lock.

IS and IX are compatible with each other. Their compatibility with whole-table shared and exclusive locks differs: IX conflicts with a whole-table shared lock, while IS does not. Neither permits an incompatible whole-table exclusive lock. Intention locks alone do not stop two transactions from updating different rows; the row-level locks govern that conflict.

AUTO_INCREMENT allocation has modes

AUTO_INCREMENT does not promise a gapless business sequence. Rollbacks, failed inserts, and concurrent allocation can leave gaps. A traditional AUTO-INC table lock is held through the statement, not through the entire transaction; not every insert in every mode takes this table lock.

innodb_autoinc_lock_modeMain behavior
0, traditionalInsert-like statements use the AUTO-INC table lock
1, consecutiveSimple inserts can reserve values with lightweight synchronization; bulk inserts can use the table lock
2, interleavedConcurrent statements can interleave allocation without that table lock

MySQL 8.0 defaults to interleaved mode. Statement-based replication cannot safely reproduce every allocation interleaving; row-based logging records the resulting row values. This is a replication-format constraint, not a reason to assume that row-based logging solves every consistency issue. See AUTO_INCREMENT handling .

Row locks are locks on index records

Ordinary consistent reads generally do not acquire row locks under READ COMMITTED or REPEATABLE READ, although they still acquire metadata locks. Locking reads explicitly request protection:

START TRANSACTION;
SELECT * FROM student_demo WHERE id = 5 FOR SHARE;
-- Older spelling: SELECT ... LOCK IN SHARE MODE;
COMMIT;

START TRANSACTION;
SELECT * FROM student_demo WHERE id = 5 FOR UPDATE;
COMMIT;

Shared record locks are compatible with other shared record locks. An exclusive record lock conflicts with shared and exclusive requests for the same record. Keep a locking read and its dependent work in the same transaction; committing releases the protection.

The important lock shapes are:

LockWhat it protects
Record lockAn index record itself
Gap lockAn interval between records, excluding its endpoints
Next-key lockAn index record plus the preceding gap
Insert intentionAn insertion position within a gap

Gap locks inhibit insertion; they are not ordinary shared/exclusive record locks. Overlapping gap locks can coexist. Insert intentions for distinct positions can coexist when they do not conflict, but an insertion can wait behind a gap lock protecting its target interval. “Insert intention” is a row-level concept, distinct from table-level IS and IX.

The original note said gap locks exist only under REPEATABLE READ. More precisely, READ COMMITTED disables gap locking for ordinary searches and index scans, but retains it for cases such as foreign-key and duplicate-key checks. See InnoDB locking .

Inspect the access path before predicting the lock range

Use a small table to reproduce behavior:

CREATE TABLE user_demo (
  id BIGINT NOT NULL PRIMARY KEY,
  name VARCHAR(30) NOT NULL,
  age INT NOT NULL,
  KEY index_age (age)
) ENGINE=InnoDB;

INSERT INTO user_demo VALUES
  (1, 'Alex', 19), (5, 'Blair', 21), (10, 'Casey', 21);

START TRANSACTION;
SELECT * FROM user_demo WHERE id = 5 FOR UPDATE;
-- From another diagnostic session:
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

In lock diagnostics, LOCK_TYPE=RECORD denotes index-level locking rather than proving that the lock excludes a gap. For ordinary index records, X,REC_NOT_GAP denotes an exclusive record lock, X,GAP denotes a gap lock, and X commonly represents a next-key lock. Inspect the index and lock data too; sentinel records and additional flags need context.

Equality on a unique index

A lookup using all columns of a unique key that finds its row generally needs a record lock rather than a preceding-gap lock. If no matching row exists under REPEATABLE READ, a locking search can protect the gap where such a row would be inserted.

Searching through a secondary index can also lock clustered-index records, particularly for exclusive locking. Do not infer the complete lock footprint from the secondary-index predicate alone.

Equality on a nonunique index

A search for age = 21 may encounter several matching entries. Under REPEATABLE READ, next-key and gap protection can prevent new entries from appearing in the searched range. Matching clustered records can also be locked. If no match exists, the relevant insertion gap can still be protected.

Range scans

The original notes describe next-key locking with record-only or gap-only boundaries for certain unique-index ranges. This is a useful starting point, but inclusivity, existing boundary values, optimizer choices, and release-specific behavior all matter. Do not promote a diagram into a universal rule that a nonunique range can never have a different boundary lock.

Full scans

A locking read, update, or delete that scans the whole table under REPEATABLE READ can lock a broad set of index records and gaps. The operational effect may resemble locking the entire table even though the mechanism remains index-level locks. READ COMMITTED has different release and gap behavior, so the same blanket statement does not apply to every isolation level.

For all these cases, examine EXPLAIN, the actual index chosen, and observed locks in a second session. The manual’s locks set by different statements is a better boundary reference than memorizing one diagram.

Safe updates are a guardrail, not lock analysis

sql_safe_updates can reject an update or delete without a qualifying key constraint or LIMIT, depending on the statement and chosen access path. It helps catch broad modifications but does not prove that a permitted statement has a small lock footprint. LIMIT also does not make an arbitrary update logically correct.

Similarly, FORCE INDEX can change a plan but should not be a default response to lock contention. Verify whether the forced access path is appropriate and whether it actually reduces the scanned and locked range.

Deadlocks and lock-wait timeouts

A deadlock is a cycle of incompatible waits. The familiar necessary conditions are mutual exclusion, holding one resource while waiting for another, no forced preemption, and a circular wait.

A two-session example is enough to see the problem:

StepSession ASession B
1Begin; update row 1Begin; update row 5
2Try to update row 5; waitHold row 5
3Continue waitingTry to update row 1; create a cycle

With deadlock detection enabled, InnoDB selects a victim and rolls back its transaction. The survivor can then proceed. SHOW ENGINE INNODB STATUS provides recent deadlock information; current waits may already have disappeared by the time they are queried.

A lock-wait timeout is different. By default, InnoDB rolls back the timed-out statement, not necessarily the entire transaction. innodb_rollback_on_timeout changes that behavior. Applications must explicitly resolve the transaction state before retrying. See InnoDB error handling .

Prevent avoidable cycles by acquiring resources in a consistent order, keeping transactions short, and indexing their access paths. Retry the complete business transaction after a deadlock with a bounded budget and backoff. Protect external side effects with idempotency; a database rollback does not retract an already sent message.

A unique order-number constraint prevents duplicate committed identifiers. It is useful for idempotency, but it does not eliminate all deadlocks or replace transaction design. Validate business invariants after concurrent fault tests rather than treating the absence of an exception as proof of correctness.
