Installing TensorFlow 2.1 with GPU Support on Windows: A Historical Note

An archived Windows setup report, covering CUDA, cuDNN, the Visual C++ runtime and the distinction between a TensorFlow smoke test and GPU verification.

Lynn LeePublished 2020-04-144 min read
Read in Chinese →

An archived study note, kept with its original date. This English reading edition clarifies version-sensitive statements; the original Chinese is available via the language switch.

Context and version scope

This note records a 2020 Windows 10 setup for TensorFlow 2.1.0 on an Intel-based Lenovo laptop with an NVIDIA GPU. It is a historical installation report, not a current TensorFlow installation guide. The original note was amended on August 1, 2020 to pin the TensorFlow package version explicitly.

The useful part of the process is the dependency chain: GPU driver, CUDA runtime, cuDNN, the Microsoft C++ runtime, and the Python package must form a compatible environment. A successful installation on one machine does not prove that an arbitrary combination is supported elsewhere.

Start from a tested compatibility matrix

The tested Windows GPU configuration for TensorFlow 2.1 used CUDA 10.1 and cuDNN 7.6. Consult the TensorFlow Windows tested-build configurations rather than choosing the newest available toolkit for an old TensorFlow binary.

The original experiment used CUDA 10.2 and later encountered a missing cudart64_101.dll dependency. That is evidence of a mismatched runtime dependency, not evidence that the newer toolkit is a drop-in replacement. This English reading edition does not repeat the old workaround of downloading an individual DLL from an unrelated download site. Use the compatible runtime from the official distribution, in an isolated environment.

Checking CUDA and cuDNN

After installing the selected CUDA toolkit, the original check was:

nvcc -V

This confirms which CUDA compiler the shell finds. It does not, on its own, prove that TensorFlow will load the expected runtime libraries.

cuDNN must match the selected CUDA version. In the historical manual installation, its headers, libraries and binaries were placed into the corresponding toolkit directories. The CUDA 10.2 directory used in that experiment was:

C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v10.2

That path describes the old experiment; it is not a recommendation to use CUDA 10.2 with a TensorFlow 2.1 wheel. Environment variables should point to the intended version, with no stale toolkit taking precedence.

The CUDA demo suite also provided a bandwidth test:

.\bandwidthTest.exe

A successful CUDA bandwidth test checks part of the driver/toolkit path. It does not validate cuDNN or the TensorFlow package, so those must be checked separately.

The Microsoft C++ runtime

The original machine already had several Visual Studio installations. Instead of adding another full IDE, I checked whether the required Microsoft Visual C++ runtime was installed and used Microsoft’s official redistributable when needed.

For a reconstructed historical environment, the runtime architecture and version must match the supported TensorFlow setup. The official source is Microsoft’s Visual C++ redistributable documentation .

Installing the Python package

The command recorded in the original article was:

pip install tensorflow-gpu==2.1.0

It belongs to that historical Python and package ecosystem. Pinning the package prevents a later release from silently changing the requirements, but it is only one part of reproducing an environment. Record the Python version, operating system, driver and GPU libraries as well.

A TensorFlow smoke test is not a GPU test

This was the TensorFlow 2-compatible version of the older graph/session smoke test:

import tensorflow as tf

tf.compat.v1.disable_eager_execution()
hello = tf.constant('Hello, TensorFlow!')
config = tf.compat.v1.ConfigProto(allow_soft_placement=True)
config.gpu_options.per_process_gpu_memory_fraction = 0.9
with tf.compat.v1.Session(config=config) as session:
    print(session.run(hello))

Older examples called tf.Session() directly. That API difference can explain why a TensorFlow 1-era example fails under TensorFlow 2; it does not necessarily mean the installation failed.

Printing a constant verifies that TensorFlow imports and executes a basic operation. Because the example permits soft placement and does not require a GPU kernel, it cannot establish that GPU acceleration works. Verify detected devices and run an appropriate operation with placement information before drawing that conclusion.

What I would keep from this experiment

Treat environment setup as a dependency problem. Use the tested version combination, distinguish compiler discovery from runtime loading, and separate a general smoke test from a test of the hardware path you actually need. Keep a record of the working environment instead of relying on screenshots or a collection of unversioned installers.
