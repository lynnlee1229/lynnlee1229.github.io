MySQL Indexes: B+ Trees, Composite Keys, and Execution Plans

Archived study notes, reorganized for English readers. The original publication date is retained. The examples focus on MySQL 8.0 / InnoDB, with qualifications added where common interview shortcuts are misleading.

What an index buys, and what it costs

An index is a structure that helps the storage engine locate records without examining every row. Depending on the query, it may also provide ordering, enforce uniqueness, or contain all the values needed for a result.

Indexes consume space and must be maintained when relevant data changes. More indexes can reduce read work while increasing write amplification, storage, and maintenance time. The objective is to support important access patterns at an acceptable total cost.

From binary search to B+ trees

Binary search locates a key efficiently in sorted data, but maintaining a large contiguous sorted array under inserts is expensive. A binary search tree avoids the need for one contiguous array, yet an unbalanced tree can degrade into a linked list. Balanced variants such as AVL and red-black trees control height.

A disk-oriented index has an additional concern: moving between nodes can require reading pages. A binary tree has only two children per node. B-trees and B+ trees use many children per node, reducing the number of levels needed for large datasets.

In a B+ tree, internal pages hold navigation entries while leaf pages hold the indexed records. Ordered links between leaves make range traversal straightforward. Smaller navigation entries increase fan-out, which is one reason B+ trees fit page-oriented storage well.

Compared with a binary tree, a B+ tree can be much shallower. Compared with a hash structure, it supports ordered and range access naturally. Hash lookup is attractive for equality searches but does not provide the same ordering. These are design tradeoffs, not a proof that one structure is fastest for every workload.

A height of three or four levels is a plausible example for some large indexes, not a universal guarantee. Key width, record size, page size, and occupancy affect height. Cached pages also mean that traversing one level does not necessarily perform one physical disk read.

How pages make a B+ tree searchable

InnoDB’s default page size is 16 KiB. Its page layout contains headers, boundary records, user records, free space, a page directory, and a trailer. Links between neighboring index pages describe logical order; the pages need not be adjacent on disk.

Within a page, records are linked in index-key order. A page directory avoids scanning the entire linked list for every search. Directory slots point to records that delimit small groups; the search first locates a group, then examines records within it. Ordinary groups are small, with special handling for the infimum and supremum boundary records.

The same principle scales across pages:

Root page: choose the child whose key range can contain the target
    -> Internal page: narrow the range again
    -> Leaf page: use the page directory, then locate the record
    -> Neighboring leaves: continue if the query needs a range

For a target key of 6, an internal entry covering [1, 7) routes the search to its child. That child narrows the range until the appropriate leaf is reached. The exact page numbers are incidental; the separation between cross-page navigation and within-page search is what matters. See the physical structure of an InnoDB index .

Clustered and secondary indexes

The clustered index contains the table’s row data at its leaves. InnoDB chooses the primary key for it when one exists. Otherwise it uses a suitable unique index whose columns are all NOT NULL; without one, it creates a hidden row identifier.

A secondary-index entry contains its indexed columns and the clustered key. If a query needs columns absent from that entry, InnoDB uses the clustered key to fetch the row. This second lookup is often called a table lookup or clustered-index lookup.

If all required values are available in the secondary index, the query can use a covering access path. Coverage is not limited to returning the primary key: the explicitly indexed columns are available too. The storage model is described in clustered and secondary indexes .

Four useful ways to classify indexes

DimensionExamples
Structure or search capabilityB-tree-style indexes, hash indexes, full-text indexes
Row organizationClustered index, secondary index
Constraint or indexed valuePrimary key, unique key, ordinary key, string prefix
Number of columnsSingle-column index, composite index

Engine support matters. InnoDB’s ordinary indexes use B+ trees. MEMORY supports hash and B-tree indexes. Full-text indexes have different semantics from ordinary ordered indexes. These labels answer different questions and should not be treated as mutually exclusive categories.

Creating primary, unique, ordinary, and prefix indexes

An index can be declared in CREATE TABLE, added through ALTER TABLE, or created with CREATE INDEX:

CREATE TABLE product (
  id BIGINT NOT NULL,
  product_no VARCHAR(32) NOT NULL,
  name VARCHAR(200) NOT NULL,
  price DECIMAL(12,2) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uq_product_no (product_no),
  KEY idx_name_prefix (name(40))
) ENGINE=InnoDB;

CREATE INDEX idx_product_no_name ON product(product_no, name);
ALTER TABLE product ADD INDEX idx_price (price);

These statements demonstrate syntax, not a recommendation to keep every index. Since product_no is already unique, the wider composite index needs a specific justification, such as a frequently used covering access path. Otherwise it may be redundant overhead.

A primary key is unique and non-null. A unique index enforces uniqueness but can permit multiple nulls when its columns are nullable. An ordinary index does not impose uniqueness. A prefix index stores only an initial portion of a string, reducing width at the expense of distinguishing power and possible coverage or ordering benefits.

Composite indexes and the leftmost prefix

An index on (product_no, name) is ordered first by product_no, then by name among equal product numbers. An index on (a, b, c) can support its leftmost prefixes (a), (a, b), and (a, b, c) for ordinary lookup patterns.

Predicates on only b, only c, or (b, c) do not identify a normal contiguous prefix range in that ordering. The optimizer may still choose a full index scan, a covering scan, or an eligible skip-scan strategy. “Missing the leftmost column makes the index completely unusable” is therefore too absolute.

The textual order of equality predicates is different from index-column order. WHERE b=2 AND a=1 can still use an (a, b) index. Reordering SQL predicates does not physically reorder the index. See multiple-column indexes .

Range predicates: separate bounds from filtering

The original notes compare these cases:

SELECT * FROM t_table WHERE a > 1 AND b = 2;
SELECT * FROM t_table WHERE a >= 1 AND b = 2;
SELECT * FROM t_table WHERE a BETWEEN 2 AND 8 AND b = 2;
SELECT * FROM t_user WHERE name LIKE 'j%' AND age = 22;

For an (a, b) index, a > 1 describes a contiguous range, but b=2 does not make all matching entries contiguous across different values of a. A later column may still be checked from index entries. Inclusive bounds can allow refinements at an endpoint in some plans, but that does not make b globally ordered throughout the range.

Similarly, a prefix LIKE may define an index range, while the later age condition still needs filtering. Collation and optimizer behavior matter. Do not memorize a rule that > always stops index use but >=, BETWEEN, and prefix LIKE never do. Inspect the chosen bounds, residual predicates, and actual scan volume. See range optimization .

key_len can help infer how much of a key participates in an access path, but it is not a count of physical bytes read from an InnoDB record. For example, a non-null VARCHAR(30) under utf8mb4 has a maximum character payload of 120 bytes, with additional length accounting in the reported key length; a non-null INT contributes four bytes. Nullable columns add further accounting. A longer key_len alone does not prove that every condition sharply reduces the scan.

Index condition pushdown

With an index on (a, b), a query using a > 1 AND b=2 may scan a range determined mainly by a, then evaluate b inside the engine before fetching full rows. Index condition pushdown can therefore reduce clustered-index lookups even when a predicate does not tighten the main search interval.

Using index condition indicates this optimization in applicable plans. It is distinct from Using index, which describes a covering access path. See index condition pushdown .

Selectivity and ordering

Distinct values divided by row count is a rough measure of column selectivity. It does not capture skew: a low-cardinality status field can still be useful when one status is rare. Nor is “put the most selective column first” a universal composite-index rule. Equality predicates, ranges, ordering, coverage, and reuse across queries all matter.

For example:

SELECT * FROM orders
WHERE status = 1
ORDER BY create_time ASC;

An index on (status, create_time) can provide ordered records within one status, whereas an index on status alone does not supply the requested time order. Validate whether avoiding a sort offsets the cost of reading the selected rows. There is no fixed “30 percent of rows” threshold at which MySQL must abandon an index. See ORDER BY optimization .

When an index is worth adding

Good candidates include required uniqueness, frequent selective predicates, and recurring order or grouping requirements that align with an index. The benefit must be weighed against write volume, index width, storage, and operational cost.

An index may be unhelpful for a tiny table, an unused column, or a predicate that retrieves most rows and still needs many clustered-index lookups. Frequently updated columns are not forbidden: they simply have a maintenance cost that the read benefit must justify. Updating an indexed value maintains the affected index structure; it does not mean rebuilding the entire index for every update.

Why a predicate may not produce an efficient index range

Several patterns deserve inspection:

  • A leading wildcard such as LIKE '%term' generally cannot use an ordinary B-tree to find a narrow starting range.
  • Applying a function or expression to a column may prevent an ordinary index on the raw value from supporting the predicate. A suitable functional or generated-column index can change the options.
  • Implicit type conversions can alter comparison semantics and usable access paths. Bind parameters with the intended types.
  • Missing leading columns of a composite index can prevent an ordinary prefix lookup.
  • An OR with an unindexed branch can make a scan attractive; other cases may use index merge or another plan.

These are reasons to inspect the plan, not a list of operations that magically disable every possible index access. An index can still be scanned or used for coverage even when it cannot locate a selective range.

Practical index-design tradeoffs

Prefix indexes. Shorter string keys can fit more entries per page. Choose a prefix based on the distribution, not an arbitrary length. A prefix does not contain the full original value, so it cannot generally cover retrieval of that value or fully establish its lexical order.

Covering indexes. An index that contains the filtering and output columns can avoid additional row fetches. For a query returning product name and price by a product identifier, evaluate a suitable composite index against simply fetching the one clustered record. Coverage is useful when it removes meaningful work, not as a goal independent of cost.

Primary-key choice. An increasing key tends to concentrate inserts near the right edge of the clustered index, whereas random keys distribute them across pages and can increase splits and fragmentation. Increasing keys still require page allocation and can create contention at a hot edge. Short clustered keys also keep secondary indexes smaller because those indexes store the clustered key.

Nullability. Use NOT NULL when the domain requires a value. Nullable fields add representation and comparison considerations, but NULL is meaningful when a value is unknown or absent. InnoDB can index nulls; replacing them with a misleading sentinel solely for indexing can damage semantics. The original row-format reading provides background on the NULL bitmap.

Reading EXPLAIN without treating it as a scorecard

FieldWhat it tells you
possible_keysCandidate indexes considered for row access
keyThe selected index, when applicable
key_lenReported length of the key used for access
rowsEstimated rows examined for the operation
typeThe access method
ExtraAdditional execution details

Common access methods include ALL for a table scan, index for an index scan, range for a range scan, ref for nonunique indexed lookup, eq_ref for a single matching row per preceding join combination, and const for a row identified through a constant unique-key lookup.

This list is not an absolute performance ranking. A scan of a small table can be the best plan. A ref lookup repeated millions of times can still be expensive. Consider row counts, loops, coverage, and ordering together.

Using filesort means an extra sort, not necessarily disk I/O. Using temporary reports a temporary result structure, not automatic evidence of an unacceptable query. Using index indicates coverage. For actual rows and timings, use EXPLAIN ANALYZE in a controlled environment; it executes the statement. See EXPLAIN .

COUNT(*), COUNT(1), and COUNT(column)

COUNT(*) counts rows. COUNT(1) counts a non-null constant for every row, so it produces the same count. COUNT(column) excludes rows where that column is null. Counting a non-null primary key therefore produces the row count, but counting a nullable business column answers a different question.

InnoDB does not maintain one exact global row count that answers every transaction’s consistent read. Different transactions may see different versions. An unfiltered count often scans a small available secondary index, but the chosen path depends on the query. COUNT(column) is not inherently forced to scan the entire clustered table; an appropriate index can support it. See aggregate function semantics .

Two optimization approaches answer different requirements:

  1. Approximation: table statistics or estimates may suffice for a rough UI count. Label them as estimates.
  2. Maintained counters: update a counter with inserts and deletes under a defined consistency model. Account for retries, concurrent updates, reconciliation, and counter contention.

The choice starts with how exact and current the count must be. Changing COUNT(*) to COUNT(1) does not solve an underlying scan-volume problem.

A review checklist

For each proposed index, identify the queries it serves, the predicates that establish a range, the conditions evaluated afterward, and any row lookups or sorting that remain. Compare actual work on representative data, then include write cost and storage in the decision. Keep the schema and plan evidence with the change so that a later regression can be explained.
