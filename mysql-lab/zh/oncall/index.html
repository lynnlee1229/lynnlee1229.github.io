EXPERIMENT 04 / BUSINESS INVARIANT

两边都提交了，却无人值班。

两名医生各自在“还有别人值班”时才撤岗。事务成功提交，仍可能共同破坏业务规则。

这里展示真实 MySQL 8.4 运行记录；浏览器不执行 SQL。实验限于固定成员，不对范围插入、任意已有快照或性能作出保证。

不变量：SUM(on_call) ≥ 1。初始状态 (1,1)，各有一次撤岗请求。独立 Python 模型枚举两种串行请求顺序，只允许 (0,1) 或 (1,0)。两方提交后，另一个自动提交观察者独立读取 MySQL 终值。

实测首跑 JSON · 停止重启后复跑 JSON · 生命周期与反例验收 · 可修改 SQL

先预测，再阅读结果

  1. 双方先完成计数，再开始写入。单行 AND on_call=1 能否保护跨行规则？
  2. 双方先建立 RR 快照，再竞争独占守卫锁。之后的普通计数会更新吗？
  3. 在首次一致性读之前获取守卫锁，或直接 FOR UPDATE 读取名单。什么证据能证明 B 真正等待？

上表每行都有两次成功提交；是否批准撤岗是另一个决策。每份记录重复三轮，第二轮交换医生 ID；第二份记录来自停止、重启后的复跑。时间只用于检查执行顺序，不作性能基准。

差异来自哪里

  • unguarded：双方在写入前都读到 2，更新不同的行并提交。RC 和 RR 都出现 (0,0) 反例。
  • late_guard：锁确实串行化了访问，但不会替换已有的 RR 读视图。RR 下后来的计数仍为 2；RC 下新的语句在这个调度中读到 1。
  • guard_first：守卫锁之前没有一致性读。B 等待 A 提交，之后首次计数读到 1。所有写入者都必须遵守协议。
  • locking_roster：当前锁定读取保护决策使用的行。B 等待后只返回一名值班医生。这里验证固定成员，不推广到所有范围或谓词场景。

  1. 基线：修改前解释失败场景为何不在模型允许的串行终值内。检查参数绑定，确认每个会话实际修改了哪名医生。
  2. 等价改写：将 count 改为 SELECT COALESCE(SUM(on_call),0) AS n FROM oncall_roster WHERE shift_id=1。复跑完整矩阵，固定名单下应保留相同语义。
  3. 负对照：从 guard 查询中删除 FOR UPDATE。所需 B→A 等待边消失，运行器必须在期限内失败，且不能产生成功 JSON。这是在拒绝失效的调度前提，并非新的终值证明。
  4. 解释把普通读取提前到 guard_first 之前，为何就变成 late_guard。用已有 late_guard RR 记录作为反例，再对比 RC。

理论与实现边界

CMU/MIT 用于理解调度、2PL 与多版本。本实验验证显式 START TRANSACTION 内的具体 MySQL 8.4 语句，不代表全部 InnoDB 读取都遵循严格 2PL，也不代表所有 RR 历史都可串行化。不需要 API key、模型、向量插件或外部数据库。
