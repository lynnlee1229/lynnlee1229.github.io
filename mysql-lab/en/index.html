A wait becomes a cycle.

A updates a; B updates b. A requests b and waits. Only after the observer sees A → B in the real wait table does B request a. InnoDB chooses a victim. The consistent-order control still waits, but both transactions commit.

EXPERIMENT 02

One transaction. Two read rules.

A establishes a plain-read snapshot at 100. B changes the row to 200 and commits. A repeats the plain read, then reads FOR UPDATE, then repeats the plain read again. A does not modify the row.

IsolationFirst plain readAfter B commitsFOR UPDATEPlain read again
READ COMMITTED100200200200
REPEATABLE READ100100200100

Both locking reads observe 200 and block B’s later update to 300 until A commits. Under RR, the following plain read still sees the original 100. This exact-row experiment does not establish gap-lock, phantom, DML or SERIALIZABLE behavior.

A: START TRANSACTION;
A: SELECT value FROM a WHERE id=1;             -- 100
B: UPDATE a SET value=200 WHERE id=1; COMMIT;
A: SELECT value FROM a WHERE id=1;             -- RC: 200 / RR: 100
A: SELECT value FROM a WHERE id=1 FOR UPDATE;  -- 200 in both
A: SELECT value FROM a WHERE id=1;             -- RC: 200 / RR: 100
B: UPDATE a SET value=300 WHERE id=1;          -- waits for A
A: COMMIT;                                  -- B can finish
EXPERIMENT 03

A plan is a claim. Execute it.

Fixed seed 20261113. Compare a full scan, a composite index, covering projection and a month-expression rewrite. Result hashes prove equivalence within each comparison; timing is machine-specific evidence.

Client wall time / median ms

One warm-up + seven measured fetches per variant. Warm shared buffer pool; no cache flush. Fixed sequential order, no randomized crossover. p95 is nearest-rank, with only seven samples.

Keep comparison boundaries clear

All variants select the same 55 IDs and dates. full_scan and composite_noncover also return amount_cents; covering projection deliberately omits that field. composite_cover and expression_month have identical full results.

Secondary InnoDB indexes contain the primary key. (tenant_id, status, created_at) therefore covers id and created_at, but not amount_cents. DATE_FORMAT requires filtering more candidate index rows than the half-open date range in this dataset.

SQL

SELECT id,created_at,amount_cents FROM events WHERE tenant_id=7 AND status='paid' AND created_at>='2026-10-01' AND created_at<'2026-11-01' ORDER BY created_at,id
