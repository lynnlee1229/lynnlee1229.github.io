  • Lec 11 Transactions and Locking
    Mar 17; PDF pages 36–48: 2PL, waits-for graphs and strict/rigorous locking

Predict：Enumerate both serial withdrawal orders. Can (0,0) occur if each request leaves at least one doctor?

python -c 'from scripts.invariant_oracle import serial_outcomes; print(serial_outcomes())'

Inspect / explain：Compare independently enumerated terminal states (0,1)/(1,0) with observer-read final_rows and oracle in every measured case.

The oracle models two fixed doctors and two requests, not arbitrary SQL serializability. This is an original Lab exercise, not a CMU/MIT assignment.

The detector resolves a complete cycle immediately. The before-cycle snapshot alone does not prove the entire cycle; use the deadlock excerpt too.

U4 / Repair write skew and test a flawed repair

  • #17 Concurrency Control Theory
    Mar 23; lecture notes sections 2, 5–6 (transactions, consistency, serial schedules)
  • Lec 12 Optimistic Concurrency Control, Snapshot Isolation
    Mar 19; lecture slides; compare snapshot theory with InnoDB's plain and locking reads
  • MySQL 8.4: Consistent Nonlocking Reads
    Reference Manual 17.7.2.3; RC statement snapshots and RR first consistent read
  • MySQL 8.4: Locking Reads
    Reference Manual 17.7.2.4; explicit transaction and SELECT FOR UPDATE

Predict：If both sessions establish a snapshot before taking the same guard row with FOR UPDATE, will serialization of the guard fix RR? What changes under RC?

python lab.py oncall --output .local/u4/oncall.json
cp sql/oncall.json .local/u4/sql.json
python lab.py oncall --sql-file .local/u4/sql.json --output .local/u4/edited.json

Inspect / explain：Both commit in all cases. Compare unguarded, late_guard and guard_first with independent final state, read barriers and real B→A guard wait.

Every writer must follow the guard protocol; guard-first RR requires no earlier consistent read. No claim about arbitrary pre-existing transactions, inserts, deletes or throughput.

U5 / Lock the data used for a decision

  • #18 Two-Phase Locking
    Mar 25; lecture notes sections 1–3 (locks, 2PL, deadlock handling)
  • MySQL 8.4: Locking Reads
    Reference Manual 17.7.2.4; explicit transaction and SELECT FOR UPDATE

Predict：Why can a locking roster read see one remaining doctor even after waiting? Is a row-local AND on_call=1 condition enough to protect a cross-row count?

python lab.py oncall --output .local/u5/oncall.json
python scripts/validate_oncall.py .local/u5/oncall.json

Inspect / explain：The follower's completed locking read returns one row; only one withdrawal occurs. The unguarded conditional updates still remove both doctors.

Fixed membership and a single shift only. Observed lock modes are recorded, not prescribed; this is not a phantom/range-insert proof. Guard rows serialize cooperating writers at the cost of contention.
