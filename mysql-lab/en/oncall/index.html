EXPERIMENT 04 / BUSINESS INVARIANT

Both committed. Nobody stayed.

Two doctors each leave only if another remains. A transaction can commit successfully and still participate in a business-rule violation.

Saved real MySQL 8.4 execution. The browser does not run SQL. This fixed-roster example makes no claim about range inserts, arbitrary existing snapshots, or performance.

Invariant: SUM(on_call) ≥ 1. Initial state (1,1); two withdrawal requests. The independent Python oracle enumerates both serial request orders and allows only (0,1) or (1,0). MySQL final rows are read separately after both participants commit.

Measured run JSON · Stop/start repeat JSON · Lifecycle & negative-control evidence · Editable SQL

Predict before reading the results

  1. Both counts finish before any write. Does a row-local AND on_call=1 condition protect the cross-row rule?
  2. Both create an RR snapshot first, then take an exclusive guard. Will the next plain count be fresh?
  3. Take the guard before the first consistent read, or read the roster FOR UPDATE. Which evidence must show B waited?

All rows above contain two successful commits. Approval is a separate decision. Each run repeats the matrix three times and swaps doctor IDs in repetition 2; the repeat follows a server stop/start. Timing is recorded only for ordering evidence, not a benchmark.

What changed, and why

  • unguarded：Both read 2 before either writes. Distinct-row conditional updates both commit; (0,0) is a counterexample under RC and RR.
  • late_guard：The lock really serializes access, but it cannot replace an existing RR read view. The follower still reads 2 under RR. Under RC its next statement reads 1 in this schedule.
  • guard_first：No consistent read precedes the guard. B waits; its first count after A commits reads 1. Every writer must obey this protocol.
  • locking_roster：A current locking read protects the rows used by the decision. B waits and then returns one active doctor. We test fixed membership, not all range/predicate cases.

  1. Baseline: explain the two disallowed terminal states before changing SQL. Read the bindings to confirm which doctor each actor changed.
  2. Equivalent rewrite: replace the count SQL with SELECT COALESCE(SUM(on_call),0) AS n FROM oncall_roster WHERE shift_id=1. Rerun the complete matrix; the semantics should match for the fixed roster.
  3. Negative control: remove FOR UPDATE from the guard query. The required B→A edge disappears and the runner must fail within its deadline without writing a success JSON. This rejects an invalid schedule assumption; it is not a new final-state proof.
  4. Explain why moving a plain read above guard_first recreates late_guard. Use the existing late_guard RR record as the counterexample, then compare RC.

Theory and implementation boundary

CMU/MIT explain schedules, 2PL and multi-versioning. This experiment verifies specific MySQL 8.4 statements with autocommit disabled via explicit START TRANSACTION. It does not establish that all InnoDB reads follow strict 2PL or that every RR history is serializable. No API key, model, vector plugin or external database is involved.
