STREAM-BATCH LAB / 02 — 架构

系统地图

一条链路，由多个数据契约组成。

逐层理解它负责什么、保存什么形态的数据，以及在哪个边界上实现一致性。

01沿数据流向阅读

持续路径是：合成业务流量 → MySQL → Flink CDC → Fluss 源表 → Flink 常规 Join。Join 结果分别写入 Fluss 宽表、独立 Iceberg 表和带 key 的 Kafka topic，再由 Kafka Engine 表和物化视图写入 ClickHouse。

Fluss 将宽表分层到 Paimon。有界 Flink 作业读取 Fluss/Paimon 的统一表，计算小时汇总，并将其行数与 Iceberg 比较。批任务的结果也经 Kafka 进入 ClickHouse。

03区分三种数据形态

  • 业务表回答“现在是什么状态”，Binlog 记录数据库行如何变化。
  • 带 key 的变更流可能包含同一订单的多个版本；消息条数不等于订单数。
  • 湖表查询读取已提交状态，不同 sink 暴露同一次变更的时间可能不同。

04Exactly-once 有明确的边界

源码配置了 Flink checkpoint，并为实时 Kafka sink 配置事务投递。仅有这些配置，不能证明整条链路不丢不重；还需检查恢复过程、消费者隔离级别、sink 提交行为和最终查询。

ClickHouse 用 ReplacingMergeTree(version) 保存多个版本，看板查询使用 FINAL 去重。当前 Kafka 入库链路不会把 tombstone 转成 ClickHouse 行删除。源端删除、服务层保留和湖表快照清理是不同的问题。

对账比较的是分别读取的两张表的行数。相同行数可能隐藏字段变化或 key 集合差异；非零差值也可能来自不同的提交进度。

05当前实现的存储与时间选择

Paimon 通过 Fluss tiering 使用本地 S3 兼容对象存储。Iceberg 使用共享 Docker 数据卷上的 Hadoop catalog。因此项目展示的是两条湖表路径，并未展示 Iceberg S3 存储或生产级共享 catalog。

Join 是配置了七天状态 TTL 的动态表常规 Join，没有定义 watermark、事件时间窗口或迟到事件侧输出。TTL 限制空闲状态的保留，状态到期后再到达的更新可能得到不同结果。

多数 SQL 和 ClickHouse 时间字段使用 Asia/Shanghai。这是实验声明的业务时区；只修改容器 TZ 变量，并不能迁移全部查询语义。
